## 1. 전사 공통 통신 원칙 & 프론트엔드 연동 가이드

### 1) 공통 응답 규격 (Envelope Pattern)
모든 API 응답은 일관된 규격으로 감싸서 전달됩니다. 프론트엔드는 `response.data.success` 여부만 확인하여 성공/실패 UI를 분기합니다.
* **성공 응답 (`200 OK`)**:
  ```json
  {
    "success": true,
    "data": { ... },
    "error": null
  }
  ```
* **실패 응답 (`400`, `404`, `500` 등)**:
  ```json
  {
    "success": false,
    "data": null,
    "error": {
      "code": "INVALID_COORDINATES",
      "message": "위도/경도 값이 유효 범위를 벗어났습니다."
    }
  }
  ```

### 2) 좌표계 및 거리 표기 원칙
* **단일 위치 객체**: `{ "latitude": 37.315891, "longitude": 126.852391 }`
  * 💡 *주의: 한국관광공사는 mapx(경도), mapy(위도)로 반환하지만, 프론트엔드에는 위도(latitude), 경도(longitude)로 정제하여 제공합니다.*
* **지도 경로 선 (Polyline 경로)**: GeoJSON 표준에 따라 `[ [경도(lng), 위도(lat)], [경도, 위도], ... ]` 이중 배열로 전달됩니다.
* **거리 표기**: 모든 거리는 **미터(m)** 단위의 정수형 숫자입니다. 프론트엔드에서 `1000m` 이상일 경우 `1.2km` 등으로 포맷팅합니다.

## 화면 1: 회원가입 및 온보딩 건강 프로필

### 1. 기능 설명 및 UI 위치
* **화면 위치**: 첫 로그인 시 노출되는 '건강 설문 모달' 및 마이페이지의 '건강 프로필 관리'
* **API Endpoint**:
  * `GET /api/user/profile` (내 건강 정보 불러오기)
  * `PUT /api/user/profile` (건강 정보 저장/수정)

| `userId` | string | O | 시스템 관리용 (화면 비노출) | 사용자 고유 식별자 (Supabase Auth UUID) | `"usr_a1b2c3d4"` |

## 화면 2: 메인 탐색 & 지도 주변 안심 장소/식당

### 1. 기능 설명 및 UI 위치
* **화면 위치**: 하단 바의 '탐색' 탭, 지도 상의 장소 마커, 장소 바텀시트(상세 카드)
* **API Endpoint**: `GET /api/places/nearby`
* **요청 파라미터 (Query)**:
  * `latitude` (number, 필수): 현재 지도 중심 위도 (예: `37.315891`)
  * `longitude` (number, 필수): 현재 지도 중심 경도 (예: `126.852391`)
  * `radiusMeters` (number, 선택): 검색 반경 (기본 3000m)
  * `category` (string, 선택): `'안심식당' | '산책로' | '관광지' | '의료'`

| 변수명 (Key) | 타입 | 필수 | UI 표시 위치 & 컴포넌트 | 상세 설명 & 비즈니스 로직 | 공공데이터 매핑 필드 |
| :--- | :--- | :---: | :--- | :--- | :--- |
| `id` | string | O | 장소 카드 고유 키 | 장소 식별 ID | TourAPI `contentid` |
| `name` | string | O | 장소명 타이틀 | 식당 또는 관광명소 명칭 | TourAPI `title` |
| `category` | string | O | 카테고리 뱃지/아이콘 | 장소 분류 (`"안심식당"`, `"산책로"`, `"관광지"`, `"의료"`) | `contentTypeId` / `cat3` |
| `address` | string | O | 주소 텍스트, 길찾기 복사 | 기본 도로명 또는 지번 주소 | TourAPI `addr1` |

| `nutrition` | object \| null | X | 안심식당 영양성분 아코디언 | 식약처 식품영양성분 API 매칭 정보 (식당일 때만 존재) | (하단 영양 상세) |
| └ `menuName` | string | O | 대표 메뉴명 | 식당의 대표 안심 메뉴 이름 | `"보리밥 정식"` |
| └ `calories` | number | O | 칼로리 표기 | 1회 제공량 열량 (kcal) | `520` |
| └ `carbohydrate` | number | O | 영양성분표 수치 | 탄수화물 함량 (g) | `75.2` |
| └ `sugars` | number | O | 영양성분표 수치 | 당류 함량 (g) - 당뇨 환자 핵심 지표 | `3.1` |
| └ `sodium` | number | O | 영양성분표 수치 | 나트륨 함량 (mg) - 고혈압 환자 핵심 지표 | `680` |
| └ `sugarGrade` | string | O | 당뇨 안심 신호등 뱃지 | 당류 기준 등급 (`"안심"`, `"보통"`, `"주의"`) | 계산 로직 반영 |

## 7. 프론트엔드-백엔드 통합 시 주의사항 및 체크리스트

1. **Null 안전성 (Optional Chaining)**
   * 공공데이터 특성상 이미지(`imageUrl`), 전화번호(`tel`), 영양정보(`nutrition`)는 없는 경우가 존재합니다. 프론트엔드에서는 `place?.nutrition?.calories ?? "정보 준비 중"` 형태로 옵셔널 체이닝 및 대체 텍스트를 구성해야 크래시가 발생하지 않습니다.
2. **상태 관리(Store) 설계 추천**
   * 프론트엔드는 전역 스토어(Zustand 등)를 다음 3개 단위로 분리하면 백엔드 API와 1:1로 깔끔하게 결합됩니다:
     * `userStore` (내 건강 프로필, 복용약)
     * `placeStore` (선택된 장소, 코스 목록, 검색 필터)
     * `walkSessionStore` (현재 진행 중인 실시간 GPS 타이머)
3. **API 모의 데이터(Mock Data) 활용**
   * 백엔드가 완전히 배포되기 전이라도, 프론트엔드 개발자는 본 명세서의 JSON Key와 타입을 그대로 활용하여 Mock Data를 만들어 UI 퍼블리싱을 100% 선행할 수 있습니다.
